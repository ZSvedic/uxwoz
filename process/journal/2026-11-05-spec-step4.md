# 2026-11-05: the spec, step 4 (review pass, panel, Export)

Step 4 of [the spec note](../plans/2026-11-05-spec-memory.md) is in the app: the review pass
(ea4aeb7), and the spec panel with Export (a7cde83). On the remade NiceSnore, a line changed in the
panel redrew the tabs of an old screen at once, and the review after the tenth pick added two open
rows in 2.3 s for about 2 cents.

## What was built

- **The review pass.** After every 5th picked screen, Sol reads the spec (with who set each line)
  and the tree, in the background ([prompt-review.md](../../spec/prompt-review.md)). Its reply
  is plain lines: `add key ? question`, `reword key = text`, `merge key, key = text`, at most 3
  of each. Code adds only keys the spec does not have, within the limits; a suggestion is stored
  for filled rows only, in its key's shape. Nothing else changes. A failure is logged and shows
  in the panel. Each run keeps its time, cost, rows added and suggestions.
- **The spec panel**: the drawer's Spec tab, also a Spec button in the toolbar. It shows how full
  the spec is (*11 of 24 lines*), the suggestions with Accept and Dismiss, the rows by section
  with where each line came from, Change or Decide, ✕ line, Delete row, a form for a line of the
  user's own, and the review's last run.
- **The user's lines win**: they are `from: user`, an Edit that tries to replace one is refused
  (*you set this row; your line wins*), and they keep the shapes. An accepted suggestion becomes
  the user's line; a merge also removes its second row.
- **Export**: the panel shows the spec as markdown, with Copy and Download. Only the spec.

## Where the note was silent

- **One line per row** counts toward the 24 (the panel's *N of 24 lines*).
- **✕ line** deletes a row's newest line, so the one before counts; a row with no question goes
  with its last line, a planned row opens again. **Delete row** asks first.
- **The browser learns of a review** by asking the server again every 2 s for up to 30 s after a
  pick that started one; the pick's reply says `reviewing: true`.
- **A review runs on picks only**: a delete that brings the count back to a multiple of 5 starts none.
- **The panel opens with no current screen**, since the spec belongs to the mockup.

## Round D: three gaps closed

Built in 5901faa:

- **Back reads `‹ Back` while `ui.back` is open.** Haiku's screens had said `Back`, `Settings` or
  nothing because its `ui.back` line was refused and the row stayed open. Once the row is filled,
  its quoted label takes over everywhere.
- **No reload when the spec changes.** The app sends each frame its tab bar and Back label by
  message, and our frame script redraws them in place, as `applyChrome` does for the first build.
  A test checks that a first build with the new spec and a redraw of the old build give the same
  screen. In the app, three `ui.nav` changes in the panel (a garbled line, its ✕ line, then the
  rename to Sleep) left Recording's live timer counting (00:00:17, :26, :36, :53) while its tab
  bar changed. Only a tab bar that goes away rebuilds the page.
- **A real suggestion.** On the Haiku NiceSnore (its cache backed up first as
  `temp/screen-cache-spec.before-suggestions.json`), three lines of the user's own doubled what was
  there: `data.score-scale` beside `data.snore-score`, and `ui.switches` beside `ui.toggles`. The
  next review, at the tenth pick, suggested on its first try:
  ```
  merge data.snore-score, data.score-scale = Snore score is 0–100; higher means more snoring.
  merge ui.toggles, ui.switches = All on/off settings use switches, never checkboxes.
  ```
  It also added three open rows (`data.severity-bands`, `data.remedy-entries`,
  `ui.recording-state`), in 2.4 s for about 3 cents. **Accept** on the first made its text the
  user's `data.snore-score` line and removed `data.score-scale` (17 lines to 16). **Dismiss** on
  the second removed the suggestion and left both switch rows as they were.

Still open from this entry: walks end at 6 to 12 screens, and the review sees only the tree, not

## Review of step 4

A critic found no path where a model changes a filled row by itself; the faults were after
Accept, in the limits, in the panel and in test cover. All 14 are fixed, with tests in
`src/tests/spec-panel.test.ts` and a few in `spec.test.ts`:

1. **A merge may not remove** the core flow, `ui.nav` or `ui.back`; the panel shows both rows'
   values now and says which row goes.
2. **A suggestion keeps the values it was made against.** When one changes (the user's line, a
   deleted row), it is stale: it does not show, and Accept refuses and drops it.
3. **The caps of 12 rules and 8 facts bind the models** (plan, review). The user's lines and an
   Edit's are bound only by the 24 lines the panel counts.
4. **The panel keeps what was typed.** A Change box stays open with its text while the panel
   redraws; a refused Save or Add keeps the text. Seen in the app: a click into another screen,
   then a refused Save (*Not saved: a ui.back line starts with its label in double quotes…*), and
   the box still read *Back sits top left*.
5. **Each count of picks is read once**, a new run replaces the suggestions not settled, rewords
   are compared after shaping, and repeats in one run are dropped.
6. **The user's key is checked first**, with its own message, and an empty line has one too.
7. **Rows the user deleted** are listed in the review request and never added again.
8. **A review that ends after Start over or Delete** is dropped.
9. **A mockup from before the spec is never reviewed**, so its screens stay as they were.
10. **Tests** for each route and guard. Two guards broken on purpose (the merge's kept rows,
    the Start-over check) each failed a test.
11. **Keys like `constructor`** are no rows: lookups read the spec's own keys only.
12. **A map fetched across a local change** is ignored, and a page opened during a review
    watches it.
13. **Saving a line unchanged** changes nothing; a model's line stays the model's.
14. **Export** takes the prompt's first line as its heading and code-quotes keys and values.

Nothing was left out.

What looked wrong, even if small:

- **Neither Home design had an `@home` tab.** The picked one is the recording screen, and its
  bar is *Record @recording, Sleep, Remedies*: Home is reachable only by Back. Code keeps Back on
  the tab screens for that reason (fix 5 of the last review), but the bar never leads home.
- **Two history screens are planned**: the plan's flow ends at `@snore-history`, the picked tabs
  name `@sleep-history`. Nothing ties the flow's names to the tabs' names.
- **`data.snore-score` stayed open** though every screen agreed on it: no design wrote the line,
  and the review does not fill rows. The user had to decide it.
- **The plan's question for `ui.back`** did not ask for the quoted label, though the planner's
  menu now does; Sol words its own questions. The picked line came quoted anyway.
- **After Undo the rail shrinks**, and ⓘ moves under the pointer: a second click opens Info.
- **Delete row's confirm** does not show in the app's browser pane (it suppresses dialogs), so the
  row was deleted through the same call the button makes. In a normal browser the confirm shows.
- **Export's heading** is the prompt's whole first line, which for NiceSnore is long.
- **The review's added rows** were about sample data (*which sessions recur across screens*): a
  real kind of disagreement, but they read like the plan's own questions, not new needs.
