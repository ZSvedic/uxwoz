# Plan: the night before review

UX Woz goes to other people for review. This plan says what one night of unattended work builds,
in what order, who does it (Fable 5.1 leads, Opus 5.5 subagents build and criticise) and how it
stays inside the budget: a Claude Max 5x plan at 28% of the week, $15 on OpenRouter, $15 on
OpenAI. The user reads [the morning report](../journal/2026-11-10-night.md) over coffee and
approves or rejects each item from a short checklist with a link to try it.

## Where the work stands

- 5,900 lines of TypeScript in `core`, `web` and `tests`; `app.ts` is 1,064 of them and every
  feature touches it. Tests are offline and run in under a second.
- The dev app calls OpenRouter (Haiku) and OpenAI (Luna, Sol, Terra). A screen costs about a cent,
  a fixer visit under a cent. Re-recording the cassettes costs a few cents.
- `benchmarks/` (180 MB, Python, last touched 2026-10-29) and the nine `src/scripts/paper-*.ts`
  experiments are finished work. Their results live in the journal.
- No git remote. The app runs on one laptop, with no users, no login and no sharing.

## Why the agent got slower, and what to do

Each step takes 40 minutes now, against 15 at the start. The code is still small, so size is a
small part of it. The larger parts:

1. **One hub file.** Every feature edits `app.ts`, `server.ts` and often `canvas.ts`, so an agent
   reads all three (2,000 lines) before it writes a line.
2. **More ceremony per step.** A step now writes a plan, a journal, spec updates, a critic pass and
   a cut pass, and looks at the app in the browser. Each is worth something; together they
   are most of the 40 minutes.
3. **Re-reading the history.** `AGENTS.md` sends a session to the journal (19 files, 3,000 lines).

What the night does about it, measured:

- **Delete finished work**: `benchmarks/`, `src/scripts/paper-*.ts` and `fixer-wording.ts`,
  the stale `launch.json` entries. Git history keeps them. `AGENTS.md` sends a session to the
  latest journal only, and names the one file a change usually needs.
- **Split the hubs along the seams that exist**: `app.ts` into the generate panel, the clicks and
  trail, the drawer and toolbar; `server.ts` into the routes and the filing chain. No new packages
  and no new indirection: the same names, smaller files, each with its own tests and its own line
  in the code map. A subagent working on the drawer then reads the drawer.
- **Measure**: for each feature, the lines an agent must read to make the change (the files it
  touches plus their contract), the wall-clock time of the build and the tokens of its
  transcript, before and after the split. The morning report prints the table.

## The budget rule

The Claude plan is the one that can run out. The 5-hour window (7% used) resets every five hours;
the weekly window (28%) resets tomorrow at 19:00 CET. The lead checks the usage card before every
subagent:

- Launch nothing when the 5-hour window is past 85%. Wait for the reset instead.
- Stop the night when the weekly window passes 90%, and write the report with what landed.
- Two subagents at a time at most, so one window is never spent in a burst.

OpenAI and OpenRouter: the night calls them only to re-record cassettes if a prompt changes
(cents) and to check features against a live screen or two (a dollar at most). Design variants,
sharing, export and voice need no model call to build.

## What the night builds

Order by value: sharing is the point of the product, export and design follow, voice last.

### Phase 0, the lead alone, 45 minutes

Delete finished work, trim `AGENTS.md`, take the baseline measurement, commit. Then one Opus
subagent splits `app.ts` and `server.ts` with a critic reading its diff; the lead runs the tests,
looks at the app and merges. One hour cap: if the split is not green by then it stays on its branch
and the features build on `main` as it is.

### Phase 1, two subagents in parallel

**Share and feedback (c and d together).** One feature, because a customer trying a mockup is a
reviewer with the view role. No accounts: a mockup gets links, one per role, each a random token.

- `view`: the player. The device frame and nothing else, the screens as they are; links between
  drawn screens work, a click on a control with no screen behind it asks *what did you expect
  here?* and records the answer. Nothing is generated, so the viewer costs the owner nothing.
- `comment`: the player plus a comment pin on any screen (and on a part, by its ID), a thumbs
  up or down per screen, and one question at the end: *would you use this?* The owner sees the
  comments and the visitor's path (screens visited, dead clicks) in a Feedback box on the canvas.
- `edit`: the full app on that mockup, spending the owner's credits. The link carries a cap on
  picks and Edits so a reviewer cannot drain the keys.
- The owner is whoever holds `UXWOZ_OWNER` from `.env`; without it the app behaves as today.
- Storage: feedback goes in the mockup's JSON next to the boxes. Async only.

**Export for a coding agent (e).** A button on the toolbar writes a zip: `README.md` (the prompt,
the devices, how the screens link), `rules.md`, `data.md` with the tables, `components.md`, one
`screens/<name>.html` per screen (the chosen version, Pico inlined, the wobbly theme as it was
drawn) and a `HANDOFF.md` that tells Claude Code, Codex or Claude Design what to build from it.
No fixer notes. The same zip is what a sharing link could offer for download later.

### Phase 2, two subagents in parallel

**Three design variants (f).** Each is one standalone HTML page under `process/design/` that
shows the app's chrome (toolbar, canvas with two cards, the boxes, the drawer) with faked content.
Each has its own palette, an inline SVG logo, its own layout idea, one animation and one action
sound made with the Web Audio API (no files). The mockup theme stays wobbly and untouched. A
fourth agent, the judge, screenshots all three on phone and desktop and writes one page of pros
and cons. Nothing touches the app's CSS until the user picks. Two rules go into `AGENTS.md` to
keep design from eating the project: a size cap on `shell.css`, and *no design tweak without a
request*.

**Voice input (g).** The browser's Web Speech API, which is free and needs no model or WASM,
instead of TamedTable's VAD and audio clips: UX Woz needs words, not audio, because an Edit is
text. The flow:

1. A microphone button starts listening. The app sleeps until it hears *hey Woz*.
2. Awake, it shows what it hears in the Edit field of the active screen. The user clicks a screen
   to make it active, as today.
3. A pause of 1.5 seconds ends the utterance. The field shows *sending in 3, 2, 1* with Cancel,
   then the Edit runs as if typed. Undo stays one click away.
4. *Woz, sleep* or *stop listening* puts it back to sleep; the button turns it off.

Safari's recognition stops after a silence and Chromium sends the audio to Google; the first is a
restart loop, the second a note in the UI. Risks the report measures: false wakes in a noisy room
and how often a pause splits one request in two.

### Phase 3, the lead

Merge what is green, run the tests and the typecheck, open each feature in the browser and take
one screenshot per item, write the morning report, commit. Anything that is not green stays on its
branch with a line in the report saying what is missing.

## How a feature is built

The same loop every time, run by the lead:

1. One Opus 5.5 builder in its own worktree, with a brief that names the files, the spec section
   to update, the test to add and what done looks like. It writes code, tests and the spec change.
2. One Opus 5.5 critic reads the diff and the spec, tries the app, and returns a list of defects
   with a failing case each. The builder fixes them. One round.
3. The lead reads the diff, runs `bun test` and `bun run typecheck`, opens the app, and merges.

## The morning report

`process/journal/2026-11-10-night.md`, in the chat style of `AGENTS.md`: one line per item, what
to click, approve or reject. For each: the branch or commit, a launch config to run it, the
screenshot, and the one thing the user should look at. Then the measurement table and the budget
spent.

## Open questions, with the answer the night assumes

- **GitHub**: not needed tonight, the laptop stays on and awake. A private repo is the next step
  anyway, because sharing links need a host. Default: push nothing tonight.
- **Hosting** for sharing links: a small machine running Bun with a disk for the JSON files
  (Fly.io, Railway, a VPS). Default: build and test on localhost tonight, deploy tomorrow.
- **Delete `benchmarks/`**: default yes, it is in git history.
- **Split first or features first**: default split first with a one-hour cap.
